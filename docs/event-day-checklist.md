## 진행 중 대응

| 상황 | 조치 |
|---|---|
| 특정 팀만 남고 인원이 안 찬다 | 팀 관리에서 해당 팀 **정원 증가** (즉시 반영) |
| 잘못 신청한 참가자 | 신청자 목록에서 **이관** (양쪽 카운트가 한 트랜잭션에서 조정됨) |
| 참가 취소자 | **취소** — 자리가 즉시 다시 선착순 대상이 된다 |
| "이미 신청했다고 나와요" | 감사 로그에서 `duplicate_name` 검색 → 누가 언제 먼저 신청했는지 확인 |
| 조기 마감 필요 | **즉시 마감** 토글 (서버가 신규 요청을 전부 `closed` 로 거부) |
| 화면이 안 갱신된다 | 무시해도 된다. 마감 판정은 항상 서버가 한다. 4초 폴링으로 대체된다 |
| 참가자가 "버튼이 안 눌려요" | 오픈 시각 전이다. 서버 시각 기준이므로 본인 폰 시계와 다를 수 있다 |

## 이의 제기가 들어오면

감사 로그에 **시각·순번·사유**가 그대로 남아 있다. `audit_log` 는 트리거로 UPDATE/DELETE 가
차단되어 있어 사후 조작이 불가능하다. 그 기록을 그대로 제시하면 된다.

`teams.seq_counter` 는 취소가 발생해도 감소하지 않는다. 따라서 **취소된 자리에는 번호 빈칸이
생긴다.** 순번이 건너뛴 것은 정상이며, 같은 순번이 두 사람에게 발급되는 일은 없다.

## 사고 시 최후의 수단

Vercel 배포가 죽는 상황은 사실상 없지만, 만약 화면이 아예 안 열린다면:

1. Vercel 대시보드 → Deployments → 직전 성공 배포에서 **Promote to Production**
2. 그래도 안 되면 신청을 **구두/수기로 받고**, 행사 후 `/admin` 에서 수동 입력한다
   (정원 초과만 지키면 된다 — 그게 이 시스템의 유일한 실패 조건이었다)
