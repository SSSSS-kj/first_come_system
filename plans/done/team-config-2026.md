# 2026 신입부원 OT 팀 구성 반영

목적: 실제 행사(2026 신입부원 OT, 동아리 약 60명)에 맞춰 팀 이름/설명/정원을
바꾼다. 선착순 로직·DB 함수·UI 동작은 건드리지 않는다.

## 확정된 값

| 정렬 순서 | 팀 이름 | 설명 | 정원 |
|---|---|---|---|
| 1 | 매크로 분석 | 금리가 오르면 어디로 돈이 움직일까? | 15 |
| 2 | 차트 분석 | 지금이 살 때인가, 팔 때인가? | 15 |
| 3 | 퀀트 투자 | 이 전략, 과거 10년엔 얼마나 벌었을까? | 15 |
| 4 | 채권 · 원자재 | 주식 말고, 세상은 뭘로 움직일까? | 15 |

총 60석. "채권 · 원자재"의 가운뎃점은 "·"(U+00B7), 앞뒤 공백 한 칸.

옛 팀 → 새 팀 대응: 거시분석→매크로 분석, 차트분석→차트 분석, 퀀트→퀀트 투자,
안전자산→채권 · 원자재.

## 작업 방식

- 한 세션에 체크 안 된 첫 태스크 하나만 진행.
- 수정 전 바꿀 파일 목록·접근 방식 1~3줄 제시 후 승인 대기.
- 최소 변경: 요청 없는 리팩터링·주석·포맷 변경 금지. `.env*` 파일은 읽지 않음
  (스크립트는 `node --env-file=.env.local`로 실행).
- 코드 변경 후 `npm run typecheck` → `npm run build`. 실패 시 원문 보고 후 수정,
  같은 에러 2회 반복 시 멈추고 보고.
- 테스트 스크립트(`scripts/*.mjs`, `e2e/*`)의 기존 검증 로직 수정은 사전 승인 필요.
- Supabase에 실행해야 하는 SQL이 생기면 완료 보고에 "SQL Editor에서 ○○ 실행 필요" 명시.
- 태스크별 커밋 분리, 체크박스 갱신. 푸시는 요청 시에만. 전부 끝나면 `plans/done/`으로 이동.

## 태스크

- [x] C1. 팀 데이터 반영
  - `supabase/seed.sql`: 위 표대로 4개 팀으로 교체(새로 세팅하는 DB용).
  - `supabase/update-teams-2026.sql` 신규: 이미 옛 팀이 들어 있는 DB에 SQL
    Editor로 한 번 실행하는 스크립트. 한 트랜잭션으로 옛 이름 → 새
    이름·설명·정원·정렬 순서를 갱신(신청 기록은 team_id로 연결되어 이름
    변경 후에도 유지). 재실행해도 안전해야 하며 다음을 처리:
    - 새 이름 팀이 이미 있으면 그 행의 설명·정원·정렬만 갱신하고 옛 이름
      팀은 건드리지 않은 채 NOTICE로 알림(seed를 두 번 돌려 8개 팀이 된
      경우 등).
    - 정원을 현재 taken보다 작게 만들 수 없으므로 taken > 15인 팀이 있으면
      전체 롤백 후 이유를 알림.
    - 마지막에 teams를 sort_order 순으로 select해 결과 표시.
  - `src/components/AdminView.tsx`의 새 팀 추가 폼 기본 정원 10 → 15
    (66행·407행 두 곳).
  - 로컬 확인: 가능하면 개발용 Supabase에 `update-teams-2026.sql` 적용
    전후 `get_public_state` 결과를 비교해 보여준다(적용은 사용자가 SQL
    Editor에서 하므로, 적용 전 결과만 먼저 보여주고 "적용했다"는 확인을
    받으면 적용 후 결과를 확인).

    4. `npx playwright test` → 기존 E2E 전부 통과(팀 이름 변경 영향 없는지 확인).
  - 결과를 `docs/verification-report.md` 끝에 "재검증 (팀 구성 변경 후)"
    섹션으로 추가(기존 섹션은 수정 금지).

  **처리 결과**: `event-sim.mjs`의 기본값만 `--users 60 --capacity 15`로
  변경(헤더 주석 예시도 함께 갱신), 실제 재실행(1~4)은 사용자 판단으로
  생략. 사유: `load-test.mjs`/Playwright E2E는 `__loadtest__`/`__e2e__`
  접두사로 자체 테스트 팀을 새로 만들어 검증하므로 실제 팀 이름·정원과
  무관하고, 좌석 확보 로직(원자적 UPDATE)은 정원 값에 관계없이 동일하게
  동작함이 이미 과거 검증(정원 1/2/3/10)에서 확인됨 — 재실행해도 새 정보를
  주지 않는다. C1에서 `get_public_state` 비교로 이름/정원 반영 자체는 이미
  확인 완료. `docs/verification-report.md`에 별도 절 추가는 생략(재실행
  결과가 없으므로).
